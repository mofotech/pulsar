LVM Storage Host Setup Guide

Date: April 2026 Applies to: Pulsar v0.5+ Author: Engineering Storage Pillar LVM + iSCSI

This guide walks through preparing a host to run the Pulsar storage agent with LVM thin-pool volumes exported over iSCSI, and configuring the compute agent host so it can discover and attach those volumes to running instances.

Architecture recap: The storage agent owns the disk — it creates LVM logical volumes and exports them as iSCSI targets via tgtd. The compute agent (on each hypervisor host) runs iscsiadm to connect to those targets and hot-plugs the resulting block device into a libvirt domain with virsh attach-disk.

Part 1 — Storage Host Setup

1.1 Identify the storage disk

Find the unformatted disk that will back the LVM volume group. Do not mount or format it — LVM manages it directly. 

# List all block devices and their mount/partition status
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT,MODEL

# Example output — /dev/sdb is unpartitioned and unformatted:
# sda    40G  disk                               (OS disk)
# sdb    50G  disk                               (storage disk — use this)
Warning: The disk you select will be completely owned by LVM. Any existing data will be destroyed. Triple-check you are targeting the correct device before running pvcreate.

1.2 Install LVM2 and tgt

apt-get update
apt-get install -y lvm2 tgt

# Enable tgtd to start on boot and start it now
systemctl enable --now tgtd

1.3 Create the LVM Physical Volume

# Replace /dev/sdb with your actual storage disk
pvcreate /dev/sdb

# Verify
pvdisplay /dev/sdb

1.4 Create the Volume Group

Pulsar's default config expects a VG named pulsar-vg. This name is configurable in pulsar.docker.yaml under agent.storage.backends.lvm.volume_group. 

vgcreate pulsar-vg /dev/sdb

# Verify
vgdisplay pulsar-vg

1.5 Create the Thin Pool

A thin pool allows over-provisioning: you can allocate more virtual storage than physically exists, with blocks consumed only as data is written. Pulsar's default thin pool name is pulsar-pool. 

# Use 95% of the VG for the pool (leave ~5% for LVM metadata overhead)
lvcreate -l 95%VG --thinpool pulsar-pool pulsar-vg

# Verify the pool was created
lvdisplay pulsar-vg/pulsar-pool

# Confirm thin pool data and metadata LVs are present
lvs -a pulsar-vg
Expected output: You should see two internal LVs: pulsar-pool_tdata (the data area) and pulsar-pool_tmeta (the metadata area), plus the pulsar-pool pool itself.

1.6 Verify tgtd is running

systemctl status tgtd

# Should show: active (running)
# tgtd binds to 0.0.0.0:3260 by default

# Confirm the port is open
ss -tlnp | grep 3260

1.7 Configure the Pulsar storage agent

Edit deploy/docker/pulsar.docker.yaml (or your agent's config file) and set the LVM details and the IP that iSCSI initiators should connect to: 

agent:
  storage:
    # Set to the IP address of this storage host on the network that
    # compute nodes use to reach it. Auto-detected if left empty.
    node_ip: "10.11.3.190"
    backends:
      lvm:
        volume_group: "pulsar-vg"
        thin_pool:    "pulsar-pool"
node_ip: This is the IP address that will be embedded in iSCSI target portals. Compute agents must be able to reach TCP port 3260 on this address. In a Docker Compose deployment with network_mode: host, this should be the host's primary network interface IP (e.g. 10.11.3.190), not 127.0.0.1.
Part 2 — Compute Host Setup

2.1 Install open-iscsi

apt-get install -y open-iscsi

# Enable the iSCSI initiator service
systemctl enable --now open-iscsi iscsid

2.2 Note the initiator IQN

Each host has a unique initiator name used to identify it to iSCSI targets. Pulsar does not restrict by initiator IQN (all initiators are allowed), but it is useful for auditing: 

cat /etc/iscsi/initiatorname.iscsi
# InitiatorName=iqn.1993-08.org.debian:01:xxxxxxxx

2.3 Verify discovery works (optional smoke test)

Before starting the Pulsar agents, confirm the compute host can reach the storage host's iSCSI port: 

# Replace 10.11.3.190 with your storage host IP
iscsiadm -m discovery -t sendtargets -p 10.11.3.190

# If tgtd is running with no targets yet, this will succeed with no output.
# If you see "connection refused", check firewall rules (port 3260/tcp).
Part 3 — Firewall Rules

iSCSI requires TCP port 3260 to be open between the compute hosts and the storage host. If ufw is active: 

# On the storage host — allow iSCSI from compute nodes
ufw allow from 10.11.3.0/24 to any port 3260 proto tcp

# Or allow from a specific compute host only
ufw allow from 10.11.3.190 to any port 3260 proto tcp

If using iptables directly:

iptables -A INPUT -p tcp --dport 3260 -s 10.11.3.0/24 -j ACCEPT
Part 4 — Docker Compose Considerations

The Pulsar Docker Compose stack runs the storage and compute agents as containers on the same host (or across hosts). Key configuration decisions:

Storage agent — host network mode

The storage agent uses network_mode: host so that tgtd binds directly to the host's network interface on port 3260. Without this, iSCSI targets would only be reachable inside the Docker bridge network. 

agent-storage:
  network_mode: host
  environment:
    - PULSAR_AGENT_CONTROLLER_GRPC=127.0.0.1:9090
  privileged: true   # required for LVM ioctls and tgtadm

Compute agent — block device access

The compute agent needs access to /dev, /sys, and the udev socket so that iscsiadm and udevadm can operate on newly-attached block devices: 

agent-compute:
  volumes:
    - /dev:/dev
    - /sys:/sys
    - /run/udev:/run/udev
  cap_add:
    - SYS_ADMIN   # iscsiadm netlink and block device operations
    - SYS_PTRACE  # libvirt/KVM ioctls

Storage agent on a separate host

If the storage agent runs on a dedicated host (not co-located with the controller), point it at the controller's public IP: 

environment:
  - PULSAR_AGENT_CONTROLLER_GRPC=10.11.3.100:9090   # controller host IP
  - PULSAR_AGENT_STORAGE_NODE_IP=10.11.3.200        # this host's storage IP
Part 5 — End-to-End Verification
  1. Start the stack 
    make up
    Wait for all services to report healthy. Check storage agent logs: 
    docker compose logs -f agent-storage
    You should see: 
    INFO  storage executor ready  vg=pulsar-vg pool=pulsar-pool
INFO  connected to controller  addr=127.0.0.1:9090 pillar=storage
  2. Create a volume type (one-time setup)
    Via the UI (Storage → Volume Types → Create Type) or API: 
    pulsarctl storage volume-type create --name standard-lvm --driver lvm
  3. Create a volume 
    pulsarctl storage volume create --name test-vol --size 5
    Poll until status is available: 
    pulsarctl storage volume list
    On the storage host, confirm the LV was created: 
    lvs pulsar-vg
# Should show an LV named after the volume UUID
  4. Attach the volume to an instance 
    pulsarctl storage volume attach <volume-id> \
  --instance <instance-id> \
  --device /dev/vdb
    While the attach is in progress (status in-use), verify on the storage host that a tgt target was created: 
    tgtadm --lld iscsi --op show --mode target
# Should show: iqn.2026-04.io.pulsar:volume.<uuid>
    Inside the instance, the disk should appear: 
    lsblk   # look for /dev/vdb
  5. Detach the volume 
    pulsarctl storage volume detach <volume-id>
    Status returns to available. The tgt target is removed and /dev/vdb disappears from the instance.
Troubleshooting
SymptomLikely causeFix
Volume stuck in creating Storage agent not connected, or LVM VG/pool not found Check docker compose logs agent-storage. Verify vgdisplay pulsar-vg succeeds inside the container: docker compose exec agent-storage vgdisplay pulsar-vg
tgtadm: command not found tgt package not installed inside container The Pulsar Dockerfile must install tgt. Add RUN apt-get install -y tgt and rebuild: make up
iSCSI discovery returns nothing tgtd not running, wrong node_ip, or firewall blocking 3260 Run systemctl status tgtd on the storage host. Verify ss -tlnp | grep 3260 shows tgtd listening. Check ufw status.
iscsiadm login failed Compute agent can't reach storage host TCP 3260 From the compute agent container: nc -zv <storage-ip> 3260. If it fails, add a firewall rule or check node_ip in config.
Block device doesn't appear after login Kernel iSCSI modules not loaded in compute container On the compute host: modprobe iscsi_tcp. Add to /etc/modules for persistence. The compute container mounts /sys and /dev from the host so host-loaded modules are visible.
virsh attach-disk fails Block device path wrong, or domain not running Verify the device exists: ls -la /dev/disk/by-path/ | grep iscsi. Confirm the instance is active. Check docker compose logs agent-compute.
Attach succeeds but guest doesn't see the disk Guest needs to rescan or the wrong target dev was used Inside the instance run lsblk. If the device is there but not visible to the app, rescan with echo '- - -' > /sys/class/scsi_host/host0/scan. Verify the device_path matches what was requested.
LV not cleaned up after volume delete Volume still in-use — detach refused delete Detach first, then delete. If the instance is gone and detach fails, manually: lvremove -fy pulsar-vg/<volume-uuid>
Quick Reference

Useful LVM commands

# List volume group
vgdisplay pulsar-vg

# List all LVs (including thin pool internals)
lvs -a pulsar-vg

# Check thin pool usage
lvs -o+data_percent,metadata_percent pulsar-vg/pulsar-pool

# Manually create a thin LV (Pulsar does this automatically)
lvcreate --thin pulsar-vg/pulsar-pool -V 10G -n test-lv

# Remove an LV
lvremove -fy pulsar-vg/test-lv

Useful tgt commands

# List all active iSCSI targets
tgtadm --lld iscsi --op show --mode target

# Manually create a target (TID must be unique integer)
tgtadm --lld iscsi --op new --mode target --tid 1 \
  --targetname iqn.2026-04.io.pulsar:volume.test

# Add a LUN backed by a block device
tgtadm --lld iscsi --op new --mode logicalunit \
  --tid 1 --lun 1 --backing-store /dev/pulsar-vg/test-lv

# Open access and delete a target
tgtadm --lld iscsi --op bind --mode target --tid 1 -I ALL
tgtadm --lld iscsi --op delete --mode target --tid 1

Useful iscsiadm commands (on compute host)

# Discover targets on a portal
iscsiadm -m discovery -t sendtargets -p 10.11.3.190

# Login to a target
iscsiadm -m node -T iqn.2026-04.io.pulsar:volume.<uuid> \
  -p 10.11.3.190 --login

# List active sessions
iscsiadm -m session -P 3

# Logout and delete record
iscsiadm -m node -T iqn.2026-04.io.pulsar:volume.<uuid> \
  -p 10.11.3.190 --logout
iscsiadm -m node -T iqn.2026-04.io.pulsar:volume.<uuid> \
  -p 10.11.3.190 --op delete

Config file reference

# pulsar.yaml — storage agent section
agent:
  pillar: storage
  controller_grpc: "127.0.0.1:9090"
  node_id: "ag-pulsar-storage-1"
  storage:
    node_ip: ""           # auto-detect primary interface IP if empty
    backends:
      lvm:
        volume_group: "pulsar-vg"
        thin_pool:    "pulsar-pool"
